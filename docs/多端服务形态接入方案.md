# 多端服务形态接入方案（Web / App / 小程序 / QQ 机器人）

> 定位：本文说明 react-base-service 作为**多端共用的 Agent 运行时基座**的设计基础、当前能力边界、缺口补齐路线，以及各端（网页、App、小程序、QQ 机器人）的接入方式与**端侧自建能力清单**。
> 配套阅读：[integration-guide.md](./integration-guide.md)（协议与接口细节）、[定时触发工作流实现方案.md](./定时触发工作流实现方案.md)（通知触达）。
> 撰写日期：2026-09-13。

---

## 1. 设计定位：基座天然面向多端

基座从设计之初就不是"某个前端的私有后端"，而是多接入方共用的运行时。支撑这一点的六个原生机制：

| 机制 | 多端意义 |
|---|---|
| **Caller 体系**：callerKey + routeValues 解析系统提示词/工具/Skill/API Key/白名单（注册接口自带 `platform` 字段） | 每个端/产品形态注册为独立接入方，能力配置互不干扰；`default` 伪 caller 还能提供跨端共享的公共资源 |
| **会话按 userName 归属**：创建/复用校验、会话列表、工具白名单均以 (userName, callerKey, routeValues, type) 为准 | 同一自然人在任意端解析出同一 userName，即得到同一份会话空间——多端同步的身份基础 |
| **回放与实时同形**：`/react/session/events` 还原的事件流与 WS 实时协议完全一致 | "换设备打开历史会话"开箱即用；各端只需实现一套事件渲染逻辑，直播与回放共用 |
| **run 状态机 + 事件全量落库**（waiting_client_message 可恢复、断线不丢） | 端可以是"薄客户端"：切端、断网、杀进程后从服务端续齐 |
| **HTTP 侧能力端无关**：附件上传、产物 COS 下载、异步任务查询、反馈、模型列表 | 不依赖 WS 的端（小程序受限场景、机器人 adapter）也能用完整周边能力 |
| **TypeScript SDK**（`/react-base-service/react/sdk/0.0.1.js`，源码 `web/sdk/`） | Web 端与 hybrid App 的连接管理/会话恢复/工具协议现成 |

目标形态：

```text
  Web 前端        App(iOS/安卓)     微信小程序        QQ 机器人 Adapter
 (TS SDK)         (原生/hybrid)    (wx.connectSocket) (独立薄服务)
    │                 │                │                  │
    └────────┬────────┴───────┬────────┴─────────┬────────┘
             │   统一鉴权网关（注入 userName / 后续 token） │
             ▼                                        ▼
   ┌─────────────────────────────────────────────────────────┐
   │              react-base-service（基座）                  │
   │   ReAct 引擎(WS) · 会话/回放(HTTP) · 工具/Skill/MCP      │
   │   附件/产物 · 异步任务 · 定时工作流(通知 webhook)         │
   └─────────────────────────────────────────────────────────┘
```

**职责边界一句话**：基座负责"想（LLM 循环）、记（会话/事件）、做（工具执行）、推（事件流/通知）"；各端负责"身份、界面、端侧能力执行、触达通道"。

## 2. 多端同步的层次定义

避免对"多端同步"的模糊期待，明确三个层次：

| 层次 | 内容 | 现状 |
|---|---|---|
| **L1 会话级同步**（拉取式） | 任意端可拉取同一用户的会话列表、完整历史回放、续聊、共享附件与产物 | ✅ **今天可用**（前提：各端使用同一 callerKey 且解析出同一 userName，见 §3.4） |
| **L2 实时多端分发** | 一个端发起 run，其他在线端同时收到直播事件 | ❌ 缺口一（当前事件只推给发起 run 的 WS 连接；过渡方案：其他端用 `/react/session/events` 按 seq 轮询） |
| **L3 离线触达** | run 完成/需要确认/定时巡检结论时，离线端收到 push（App 厂商推送、小程序订阅消息、QQ 消息本身） | ⚠️ 部分可用（QQ 端天然具备；通用 push 依赖基座通知 webhook + 各端自建推送通道） |

服务端已保证**同一会话同时只有一个活跃 run**（事务级互斥），多端并发写不会冲突——这是同步正确性的地基，已就位。

## 3. 基座缺口与补齐路线

### 3.1 P0：统一鉴权与身份（多端同步的前提）

- 现状：免鉴权，完全信任 `X-User-Name` 头。网页端经自有登录网关注入用户名可行；App/小程序/机器人直连等于任何人可冒充任何用户。
- 补齐：可开关的鉴权中间件（JWT 或 caller 级 API Key + 签名），校验通过后映射出 userName；保留 anonymous 兼容模式用于内网/演示。改造点：`middleware/` 新增鉴权链 + `tblLlmCaller` 增加 caller 级密钥字段。
- 原则：**鉴权可以在基座做，也可以在网关做，但只能做一次**；统一用户身份（同一自然人 → 同一 userName）必须在接入前定义清楚。

### 3.2 P1：会话级事件订阅通道（L2 实时分发的主体）

- 补齐：新增"按 sessionId 只读订阅"端点（SSE 或 WS），事件经 Redis pub/sub 分发，支持多个连接同时订阅同一会话的实时流；客户端带 seq 游标续读（事件信封已有 seq，天然增量）。
- 效果：任意端打开任意会话 = 直播 + 从断点续读；配合回放接口，切端体验闭环。
- 改造点：`service/react/ws.go` 旁路新增订阅入口 + 事件总线（run 的 EventWriter 串行写 WS 的同时 publish）；不改 run 互斥与事件落库逻辑。

### 3.3 P2：通用通知触达（L3）

- 复用[定时触发工作流实现方案](./定时触发工作流实现方案.md)的 webhook 通知机制，扩展为 run 级事件通知（run 完成、waiting_client_message 等待用户、巡检结论）→ 各端推送网关（App 厂商推送 API / 小程序订阅消息 / QQ 主动消息）由端侧或 BFF 消费。

### 3.4 会话跨端复用策略（设计决策，非代码缺口）

会话复用要求 userName/callerKey/routeValues/type **完全一致**，由此有两种接入模式，按产品形态选择：

| 模式 | 做法 | 效果 | 适用 |
|---|---|---|---|
| **A：跨端同 caller** | Web/App/小程序共用一个 callerKey（如 `my-app`），routeValues 表达页面差异 | 同一 userName 的会话在所有端可见、可续——L1 同步开箱即用 | 面向同一批用户的消费级产品 |
| **B：按端独立 caller** | 如 `web-app` / `qq-bot` 各一套 | 会话与能力配置完全隔离 | 交互形态迥异的端（QQ 机器人：纯文本、无 client 工具、提示词不同） |

> 若未来出现"模式 B 的端也要看模式 A 的会话"的需求，再评估将会话查询放宽为按 userName 跨 caller（涉及权限语义，暂不做）。

## 4. 各端接入指南

### 4.1 通用接入步骤（所有端相同的前置）

1. `POST /caller/register` 注册接入方（`platform` 标注端形态）；
2. `POST /apikey/register` 配置 caller 级模型凭证；
3. `POST /system-prompt/register` 配置该端的系统提示词（按 routeValues 拆多条）；
4. 按需注册工具（http/client/mcp 三类）与 Skill；
5. 端侧实现协议子集：上行 `run` / `cancel` / `tool_use_answer` / `client_tool_use_end`，下行事件按需消费（最小集：`content_delta`、`tool_use_start/end`、`done`、`error`）。

### 4.2 Web 端

- **接入**：直接嵌入 TS SDK（连接管理、心跳、会话恢复、client 工具协议已封装）；历史侧边栏走 `/react/session/list`，回放可直接链到内置 `/react/replay` 页或自渲染 `/react/session/events`。
- **端侧自建能力清单**：
  - 登录态与网关：自有账号体系 → 网关注入 `X-User-Name`（P0 后改 token）；
  - 结构化 UI 渲染：计划确认卡片（`create_plan`）、todo 进度、工具调用卡片、附件/产物预览（COS 下载链接）、模型切换 UI；
  - **client 工具的端侧执行**：`client_tool_use_start` → 前端能力（跳转页面、选人选址、调起支付等）→ `client_tool_use_end` 回填——client 工具的价值就在各端实现自己擅长的事；
  - `ask_question` 问答 UI（结构化澄清表单）。

### 4.3 App 端（iOS / Android / hybrid）

- **接入**：原生 WS 客户端或复用 TS SDK（hybrid/React Native 场景）；HTTP 周边能力（附件上传/产物下载/异步任务）直连。移动网络下注意 WS 保活（协议层 5s ping 由客户端回 pong，应用层 20s heartbeat）与断线重连后**用 `/react/session/events` + seq 补齐漏掉的事件**（回放同形保证渲染逻辑复用）。
- **端侧自建能力清单**：
  - 账号体系与登录（映射统一 userName）；
  - 推送通道接入（厂商推送/个推），消费基座 P2 通知 webhook；
  - client 工具子集：扫码、定位、相册/拍照上传（先走附件上传接口拿 fileId）、支付；
  - 后台/杀进程策略：run 期间退后台依赖服务端状态机兜底，回前台拉事件续读；
  - 与 Web 相同的结构化 UI 渲染（建议抽出共享渲染层）。

### 4.4 微信小程序

- **接入**：`wx.connectSocket` 连 WS（注意：需 wss 且域名进后台白名单；小程序同时 WS 连接数有限，全局复用一条连接）；HTTP 接口走 `wx.request`。鉴权必须走服务端中转（wx.login code → 业务后端换会话 → 注入 userName / token），不可在前端直存凭证。
- **端侧自建能力清单**：
  - 登录链路：wx.login → 自有后端 → 统一 userName；
  - 订阅消息推送（需用户授权订阅模板）；
  - client 工具子集：获取位置、扫码、支付、选择文件；
  - 富文本/Markdown 渲染（小程序无原生 markdown，需组件库）与长回复分页；
  - 产物下载（COS 链接在小程序内受 downloadFile 域名白名单限制，必要时经业务后端中转）。

### 4.5 QQ 机器人（adapter 形态）

QQ 是纯文本消息通道，**必须经一个薄 adapter 服务接入**，不与基座直连：

```text
QQ 官方机器人平台(WebSocket/Webhook) 或 OneBot 协议端(NapCat 等)
        │  消息/事件回调
        ▼
┌────────────────────── QQ Bot Adapter（自建薄服务）──────────────────────┐
│ ① 身份映射：QQ openId/userId ↔ 统一 userName（映射表）                    │
│ ② 会话策略：私聊=每用户固定会话；群聊=每群固定会话（复用上下文+自动压缩）  │
│ ③ 上行翻译：QQ 消息 → ReactRunPayload（callerKey=qq-bot，模式 B）        │
│ ④ 下行翻译：content_delta 聚合为完整回复 → 按QQ消息长度限制分片发送；      │
│    thought 不发；tool_use_start/end 降级为"[正在调用 xx 工具]"摘要        │
│ ⑤ 结构化交互降级：ask_question → 文本选项("回复 1/2/3") → tool_use_answer；│
│    client 工具：该 caller 不注册 client 类工具（能力裁剪）；              │
│    create_plan：caller 配置 allow_plan:false 直接关闭（纯文本端不适用）   │
│ ⑥ 并发治理：同一用户连发消息时排队或回复"正在处理中"（会话单 run 互斥）；  │
│ ⑦ 富媒体：产物/图片经 COS 链接转 QQ 图片消息                             │
└──────────────────────────────────────────────────────────────────────┘
        │  WS / HTTP（以服务身份或映射后的 userName 访问）
        ▼
   react-base-service
```

- **接入**：注册独立 caller（模式 B）；提示词为"消息化"版本（要求模型输出适合 IM 阅读的短段落、避免超长代码块）；工具只挂 http/mcp 类型（服务端可执行），不挂 client 工具。
- **端侧（adapter）自建能力清单**：上图的 ①–⑦；QQ 平台侧的机器人注册、回调验签、主动消息配额管理；可选：群聊多主题会话路由（按消息引用/关键词切换会话）。
- **加分项**：adapter 顺便就是 L3 触达通道——基座 P2 通知 webhook 可推给它，由它发 QQ 主动消息（巡检报告推送、等待确认提醒）。

## 5. 端侧自建能力总表（"接完之后自己要做什么"）

| 能力 | Web | App | 小程序 | QQ Bot(adapter) | 说明 |
|---|---|---|---|---|---|
| 账号/登录 → 统一 userName | 自有登录+网关注入 | 自有账号 | wx.login 中转 | QQ id 映射表 | **多端同步的前提**，P0 前各端自担，P0 后对接基座鉴权 |
| WS 连接管理/断线续读 | SDK 已含 | 自实现或 SDK | wx.connectSocket | adapter 内轮询/WS | 断线后 `/react/session/events`+seq 补齐 |
| 结构化 UI（计划/todo/工具卡片/产物） | 必做 | 必做 | 必做（受限） | 降级为文本 | 回放同形协议 → 渲染逻辑可跨端共享 |
| client 工具端侧执行 | 按需 | 扫码/定位/支付 | 位置/扫码/支付 | **不注册** | client 工具 = 各端的差异化能力出口 |
| ask_question 应答 UI | 表单 | 表单 | 表单 | 文本选项回复 | 统一走 `tool_use_answer` |
| 推送/触达 | 站内 | 厂商推送 | 订阅消息 | QQ 消息 | 消费基座通知 webhook（P2） |
| 内容合规/审核 | 按需 | 按需 | 平台强制 | 平台强制 | 各端平台要求不同，基座不代管 |

## 6. 落地顺序建议

1. **先 Web**（SDK 现成，验证 caller 配置与工具体系）；
2. **P0 鉴权中间件**（App/小程序/机器人上线前必须）；
3. **App/小程序**（协议子集 + client 工具子集，体验同 Web）；
4. **P1 事件订阅通道**（多端同时在线的直播需求出现时）；
5. **QQ Bot adapter**（独立 caller + 消息降级策略，附带成为推送通道）；
6. **P2 通知触达**（定时巡检结论、等待提醒推到各端）。
