# 知识库与长期记忆集成改造方案（RAGFlow + Graphiti）

> 目标：为 ReAct 基座补齐**跨会话的知识与记忆能力**，分三层落地——
> **文档知识库（RAGFlow）**、**时序事实图谱记忆（Graphiti）**、**统一检索与注入**。
> 前置调研：《[ragflow-admin学习.md](./ragflow-admin学习.md)》《[graphiti学习.md](./graphiti学习.md)》；
> 原始选型讨论存档于《知识库集成、长期记忆、检索.md》。
> 本文所有"现有模式"均指 main 分支现状：记忆模块 P1-P3 已实现（`docs/memory.md`）、
> 子 Agent 委派 P1 已实现（`docs/子Agent委派P1实现说明.md`）、MCP 客户端与动态连接管理已实现（`docs/mcp.md`）。

---

## 1. 背景与目标

### 1.1 现状与缺口

| 现有机制 | 覆盖范围 | 缺口 |
|---|---|---|
| 长期记忆（`service/react/memory.go`，MySQL 条目层） | 用户偏好、身份约定、SOP 类原子事实（resident/detached + reflection） | 无实体关系、无时间演化（"上个月部署在哪"答不了）、检索是 LIKE 关键词（P4 向量检索待做） |
| 上下文压缩 / 会话回放 | 单会话内 | 会话结束即失效 |
| Skill / 系统提示词 | 静态知识，人工维护 | 无法沉淀文档型知识（PDF/手册），无语义检索 |
| repo MCP 适配器 | 本地代码仓库检索 | 非文档知识库，无向量化 |

### 1.2 目标分层

```
┌────────────────────────────────────────────────────────────┐
│                    ReAct 运行时（Go 基座）                    │
│                                                            │
│  system 前缀注入：<memory>（现有）+ <knowledge> + <graph_memory> │
│                                                            │
│  工具：memory_list/read/write（现有）                        │
│       knowledge_search（新增）                               │
│       graph_memory_search / graph_memory_write（新增）        │
└──────┬────────────────────────┬────────────────────────────┘
       │                        │
       ▼                        ▼
┌─────────────────┐   ┌──────────────────┐   ┌─────────────────────┐
│ Layer1 常驻核心记忆 │   │ Layer2 时序事实图谱 │   │ Layer3 文档知识库      │
│ MySQL（现有，不动） │   │ Graphiti+FalkorDB │   │ RAGFlow             │
│ 我是谁/偏好/SOP    │   │ 实体/关系/时间事实   │   │ 手册/文档/结构化资料   │
│ 每次必在场/可审计   │   │ 按需检索/自动失效    │   │ chunk 级混合检索      │
└─────────────────┘   └──────────────────┘   └─────────────────────┘
```

三层的分工判据（写进各工具 description，教模型分流）：

| 问题形态 | 走哪层 |
|---|---|
| "用户是谁、有什么偏好、我们的口径约定" | Layer1（现有 memory 工具） |
| "A 和 B 什么关系、过去发生过什么、现在 vs 上个月的状态" | Layer2（graph_memory） |
| "手册/规范/文档里怎么写的" | Layer3（knowledge_search） |

                               ▼                   ▼
                ┌──────────────────────┐  ┌─────────────────────┐
                │  RAGFlow (docker)    │  │ graphiti-mcp :8000  │
                │  api :9380           │  │  └─ FalkorDB :6379  │
                │  ES/MinIO/MySQL/Redis│  │  └─ LLM/Embedder ───┼──► 基座现有

关键决策总表（后文分述理由）：

| 决策点 | 结论 | 备选（何时考虑） |
|---|---|---|
| RAGFlow 接入通道 | **原生 Go 客户端 + 内置 meta tool**（P1 即做） | http 型注册工具仅用于当天冒烟验证 |
| 是否直读 RAGFlow MySQL | **不直读**（ragflow-admin 的教训：schema 耦合扛不住升级） | — |
| Graphiti 接入通道 | **P1 先用现有 MCP 动态连接零代码验证；P2 落 Go 客户端 + 内置工具**（服务端强制 group_id） | — |
| 图数据库 | FalkorDB（单容器轻量起步） | Neo4j（存量企业环境） |
| Graphiti 模型供应商 | OpenAIGenericClient 指向基座网关 | 独立 OpenAI key |
| 记忆 P4（向量检索） | **重新定义为"由 Layer2/3 承担"**，MySQL 条目层维持 LIKE | 条目量单 owner > 数千且不引入 Graphiti 时再做嵌入 |
| 写入 Graphiti 的时机 | P1 模型主动；P2 run 收敛后异步回灌；P3 reflection 桥接 | — |

## 3. 模块一：RAGFlow 知识库接入

### 3.1 为什么是原生客户端而不是 http 工具

http 型工具（`service/tool/executor.go::ExecuteHTTPTool`，config={url,method,headers}）当天就能接通 `/api/v1/retrieval`，但产品化差三口气：

1. **结果规整**：RAGFlow 返回的 chunks 需要 normalize（content/score/documentName/highlight 统一裁剪、超长走 resultRef 分片），裸 JSON 直接回填模型浪费 token 且格式不稳；
2. **权限**：dataset 必须按 caller 白名单过滤——不能让模型任意传 `dataset_ids` 读到别人的库；工具 config 里的静态 dataset 列表做不到"caller×dataset"的动态绑定；
3. **索引注入**：`<knowledge>` 块需要"当前 caller 可用哪些知识库（名称+描述）"的元数据，这本身要一张注册表。

### 3.2 代码落点（对齐现有分层）

```
service/knowledge/
├── client.go        # RAGFlow HTTP API v1 客户端：dataset list/create、doc upload/parse、retrieval
├── client_test.go
└── service.go       # 业务层：caller 白名单校验、结果 normalize、KB 注册表读写
models/llm/knowledge.go        # tblLlmKnowledgeDataset 模型（GORM，风格对齐 memory.go）
controllers/http/knowledge/    # /react/knowledge/* 管理接口（风格对齐 controllers/http/agent）
service/react/knowledge_tools.go  # knowledge_search meta tool（风格对齐 service/react/memory.go）
service/react/knowledge_inject.go # <knowledge> 索引块渲染（对齐 renderMemoryContext）
```

### 3.3 模型侧工具：knowledge_search

注册进 `runtimeToolDefinitions`（与 `memoryToolDefinitions()` 同款：`llm.react.knowledge.enabled` 开关控制，受 ExecutionProfile 管控），走现有两段式加载（摘要索引 → get_tool → execute_tool）：

```json
{ "name": "knowledge_search",
  "description": "在知识库中检索文档片段。适用于：查手册/SOP/规范/历史文档原文。输入自然语言查询，返回最相关的文档片段（含出处）。当前可用知识库见系统提示词 <knowledge> 块。",
  "parameters": {
    "query":       "自然语言查询，必填",
    "datasetIds":  "可选，限定知识库；缺省=检索当前全部可用知识库",
    "topK":        "可选，默认 8，上限 20",
    "threshold":   "可选，相似度阈值，默认取服务端配置" } }
```

行为：

- 服务端把 `datasetIds` 与 caller 注册表（`tblLlmKnowledgeDataset`）求交集，**空交集直接报错**并提示可用知识库（防越权 + 自纠错，同 `memory_read` 作用域校验思路）；
- 结果 normalize 为 `[{content, score, documentName, datasetName, highlights?}]`，超 `inline_limit_bytes` 自动走 resultRef（复用 `normalizeToolResult`）；
- 失败/超时（默认 15s）按错误回填，不打断 run。

### 3.4 KB 注册表与索引注入

新表（DDL 见 §7）：`caller_key + dataset_id` 唯一，带 `name/description/status`。`description` 是检索质量的抓手（教模型什么时候该查这个库），管理面必填。

run 初始化时（`prepareRuntimeRequest`，与 Skill 摘要同通道）拼进 system 前缀：

```text
<knowledge>
## 可用知识库（用 knowledge_search 检索，不要凭空回答文档类问题）
- [Hive 运维手册] 故障案例、性能调优 SOP（datasetId: 7a2f…）
- [报销制度] 差旅/报销口径与流程（datasetId: 91bc…）
</knowledge>
```

注册表为空或 `knowledge.enabled=false` 时整个块不出现（零 token 回归，与 `<memory>` 同款约束）。

### 3.5 管理面（P1 最小集 + P3 补全）

| 接口（挂 reactGroup） | 阶段 | 说明 |
|---|---|---|
| `POST /react/knowledge/list` | P1 | 列出 caller 下已绑定知识库（含 RAGFlow 侧实时 doc_num/token 统计） |
| `POST /react/knowledge/bind` / `unbind` | P1 | 绑定/解绑已有 RAGFlow dataset 到 caller（含 description） |
| `POST /react/knowledge/dataset/create` | P3 | 在 RAGFlow 建库并绑定（透传 embedding/rerank 模型配置） |
| `POST /react/knowledge/document/upload` | P3 | 上传文档（复用附件上传通道的文件来源） |
| `POST /react/knowledge/document/status` | P3 | 解析状态：`run/progress` 语义（UNSTART/RUNNING/DONE/FAIL + 进度），**前端条件轮询**（有 RUNNING 才 3s 轮询）——语义抄 ragflow-admin，数据源用 RAGFlow 官方 API 轮询而非直读库 |
| `POST /react/knowledge/document/parse` / `stop` | P3 | 触发/停止解析 |

P3 的异步解析任务可选用 `service/asynctask` 的 Provider 同步框架回写状态（可选增强，非必须）。

### 3.6 RAGFlow 部署要点

- 官方 docker compose（含 ES/Infinity、MinIO、MySQL、Redis），**资源预算 ≥4C8G**，与基座同内网；
- 只用官方 HTTP API v1（`/api/v1/dataset`、`/api/v1/retrieval`…），服务账号 API Key 放基座配置；
- 检索质量参数集中在基座侧配置（`top_k/similarity_threshold/rerank`），rerank 模型在 RAGFlow 侧配置；
- **不做跨用户管理台**（ragflow-admin 的场景），知识库按"基座服务账号持有 + 基座注册表分配给 caller"的单租户模型起步；确有多团队隔离需求时再按 caller 建多个 RAGFlow 用户/API Key。

## 4. 模块二：Graphiti 时序记忆接入

### 4.1 通道决策与 group_id 治理（本模块最重要的安全设计）

Graphiti 官方暴露两条服务化通道：FastAPI REST（`POST /messages` 202 异步、`POST /search`、`POST /get-memory`）与 MCP server（`add_memory`/`search_memory_facts`/`search_nodes`…，工具入参**支持逐调用传 `group_id`**，缺省回落 CLI `--group-id`）。

分两步走：

- **P1（零代码验证）**：用现有 MCP 动态连接管理（`POST /react/mcp/create`，`kind: http` 或 `http_sdk`）登记 graphiti-mcp，工具自动同步进 `tblLlmTool`，模型立即可用。**仅限信任环境**：此时 `group_id` 是模型可控入参，存在跨组读写面——单租户或全员共享图时接受，多租户必须上 P2。
- **P2（产品化）**：`service/graphmemory` Go 客户端（优先打 REST；或内部仍调 mcpclient）+ 内置 meta tool，**group_id 由服务端按 run 上下文强制注入，不出现在工具参数里**：

```
group_id 映射（与记忆模块 owner 两级同构）：
  graphMemory.group_scope = caller       → "{callerKey}"
  graphMemory.group_scope = caller_user  → "{callerKey}__{userName}"   # [a-zA-Z0-9_-] 合法
```

MCP 端点在内网时需 `mcp.allow_private_endpoint: true`（SSRF 放行开关，仅限内网部署，语义见 `docs/mcp.md` §4）。

### 4.2 模型侧工具

P2 注册（`llm.react.graphMemory.enabled` 开关，风格对齐 memory 三件套）：

```json
{ "name": "graph_memory_search",
  "description": "检索长期事实图谱：实体间关系、历史事件、随时间变化的状态。适用于『A 和 B 什么关系』『过去发生过什么』『某个状态什么时候变的』。返回带时间窗的事实。",
  "parameters": {
    "query":        "自然语言查询，必填",
    "centerEntity": "可选，围绕某实体扩展检索",
    "validAtFrom/validAtTo": "可选，事实有效期过滤（问历史状态时用）",
    "limit":        "默认 10" } }
```

P3 增补写入工具（模型显式沉淀，如用户说"把这次结论记下来"）：

```json
{ "name": "graph_memory_write",
  "description": "把一段重要事件/结论写入长期事实图谱（异步生效）。仅在用户明确要求沉淀、或发现值得长期记住的事实时使用。",
  "parameters": { "name": "短标题", "content": "事件或事实描述（自然语言）",
                  "sourceType": "text|message|json，默认 text" } }
```

服务端固定补齐：`group_id`（按 §4.1 映射）、`reference_time=now`、`source_description="react-base run {runId}"`（溯源进 episode）。

### 4.3 写入链路（三级递进）

| 级别 | 触发 | 机制 | 阶段 |
|---|---|---|---|
| W1 模型主动 | 用户显式"记住这个" | `graph_memory_write` 工具 | P3 |
| W2 会话收敛回灌 | run 正常 finish | `finish()` 收敛点挂异步 goroutine（生命周期独立于连接，参照 memory reflection 的派生模式）：把本 run 的用户输入 + 最终回答 + 关键工具轨迹格式化为 episode（`source=message`，`reference_time=run 开始时间`），POST /messages（202 队列） | P2 |
| W3 整理桥接 | `compact_end` reflection | reflection run 的受限工具集增加**只读** `graph_memory_search`，供整理 Layer1 条目时参考图谱事实 | P3（可选） |

W2 的写入纪律（配置化闸门，防成本失控）：

- `min_user_messages`（太短的 run 不写）；
- `require_tool_use=true`（默认只回灌发生过工具调用/委派的"做事"会话——纯闲聊不值得 3-4 次 LLM 抽取成本）；
- 进程内冷却与队列长度上限（Graphiti 侧 QueueService 已按 group 串行，基座侧再加全局水位）；
- 失败静默重试一次后仅记日志 + `react_graph_memory_episode_total{status=error}` 指标，绝不影响主会话（与 reflection 同款承诺）。

### 4.4 读注入：`<graph_memory>` 块

run 初始化（`buildKnowledgeContextForRun` 同期）异步检索、有则注入：

```
查询 = 本 run 用户首条输入（或会话 last_message）
→ Graphiti search（基础 EDGE_HYBRID_SEARCH_RRF，limit=inject.max_facts）
→ 渲染：
<graph_memory>
## 相关历史事实（自动检索，可能包含已失效事实，注意时间窗；深挖用 graph_memory_search）
- [2026-08-01 ~ 2026-09-01] service-A 部署在 cluster-01
- [2026-09-01 起] service-A 部署在 cluster-02
</graph_memory>
```

约束：事实条数/字符双预算（默认 8 条 / 1200 字符）；检索失败静默跳过（注入是增强不是依赖）；空结果不渲染块。检索超时预算 1.5s，超时放弃注入（不阻塞 run 启动主链路，可与 LLM 首轮并行）。

### 4.5 与现有 MySQL 记忆模块的关系（不重构，只分工）

| | Layer1 MySQL 条目（现有） | Layer2 Graphiti 图谱（新增） |
|---|---|---|
| 内容 | 偏好/身份/口径/SOP——"必须准确、必须在场" | 实体/关系/事件——"越多越好、按需召回" |
| 注入 | 常驻层全文（每 run 必在） | 相关事实检索（按本次话题） |
| 写入 | 模型/管理面/reflection，统一写核心+修订流水 | episode 异步抽取，官方管道 |
| 审计 | 修订流水表，可回滚 | episode 溯源 + 失效不删除 |
| 失效语义 | 显式 update/delete | bi-temporal 自动失效 |

冲突策略：两者可能记载矛盾事实（如用户口头纠正 vs 图谱旧事实）——以 Layer1 为准（它有 reflection 主动维护），工具 description 与 `<graph_memory>` 头部声明"以 `<memory>` 块为准"。

### 4.6 运维场景第一版本体（P3 落 YAML）

```
实体：Service / Cluster / Job / Table / Dataset / Incident / Error / Solution / User
关系（edge_type_map 节选）：
  Service  → DEPLOYED_ON → Cluster；Service → DEPENDS_ON → Service；Service → CAUSED → Incident
  Job      → READS_FROM / WRITES_TO → Table；Job → FAILED_BECAUSE → Error
  Incident → CAUSED_BY → Error；Incident → RESOLVED_BY → Solution
```

Graphiti MCP server 支持 YAML 配置本体（不改 Python）；字段即节点/边 attributes（如 Service.owner、Table.database）。

### 4.7 部署要点

- `falkordb`（单容器）+ `graphiti-mcp`（`--transport http --database-provider falkordb`，端口 8000，端点 `/mcp/`）；
- LLM/Embedder：`--llm-provider` 走 OpenAI 兼容端点（`OpenAIGenericClient`），指向基座网关；`EMBEDDING_DIM` 与所选嵌入模型一致（P0 验证项）；
- Reranker：非 OpenAI 部署选 BGE（本地）或 Gemini，factories 已保证不回退到需 OpenAI key 的默认；
- 遥测 PostHog 内网部署关闭；`SEMAPHORE_LIMIT` 按网关限速下调。

## 5. 模块三：统一检索与记忆 P4 决策

### 5.1 检索入口的统一语义

不做"一个 query 打三层"的联邦检索器（过度设计）；统一体现在**模型侧的分流协议**上：三层各有注入块与工具，description 里的分流判据（§1.2 表）就是"路由器"。观察一个阶段后，若模型分流质量差，再考虑 P4+ 做服务端联邦（一个 `unified_retrieve` 工具内部并发三层、RRF 合并——Graphiti 的 RRF 实现可直接抄）。

### 5.2 记忆 P4（向量检索）的重定义

`docs/memory.md` P4 原计划"description 嵌入 + 向量检索"。引入 Layer2/3 后调整：

- 语义召回诉求大部分由 Graphiti（事实）与 RAGFlow（文档）承接；
- Layer1 保持小而精（常驻≤16 条 + 单 owner 软上限 500 条），LIKE + tags 过滤在此量级够用；
- **P4 改为条件触发**：仅当某 owner detached 条目持续超软上限且未启用 Graphiti 时，才做嵌入检索；否则挂起。避免两套向量基础设施。

## 6. 与现有模式的对接点汇总

| 现有机制（文件） | 复用方式 |
|---|---|
| Meta Tool 注册表 `service/react/meta_tools.go::runtimeToolDefinitions` | knowledge_search / graph_memory_* 同款注册，配置开关控制（对齐 memory 三件套） |
| 两段式工具加载（get_tool/execute_tool） | 新工具天然纳入：摘要索引自动生成、定义指纹、ExecutionProfile 拦截 |
| system 前缀注入通道（skill 摘要 / `renderMemoryContext`） | `<knowledge>`、`<graph_memory>` 块同通道拼装（`prepareRuntimeRequest`） |
| 工具大结果 resultRef（`normalizeToolResult`） | 检索结果超限自动分片，`read_tool_result` 回读 |
| MCP 动态连接（`service/mcpclient`、`tblLlmMcpServer`） | P1 零代码接 graphiti-mcp；工具自动同步、启停、caller 绑定 |
| http 型工具（`service/tool/executor.go`） | RAGFlow 冒烟验证用；产品路径不走 |
| 资源注册 CRUD 模式（`service/agent/agent.go` + `controllers/http/agent`） | `/react/knowledge/*` 管理面同构 |
| 反思派生 run 模式（`service/react/memory_reflection.go`） | W2 写入 goroutine 的生命周期/静默失败/指标范式 |
| 异步任务 Provider 框架（`service/asynctask`） | P3 文档解析状态同步（可选） |
| 作用域两级模型（caller / caller_user） | KB 绑定 caller；graphiti group_id 同构映射 |
| `/metrics` 指标惯例 | `react_knowledge_search_total{status}`、`react_graph_memory_episode_total{status}`、注入块渲染水位 |

## 8. 实施计划

| 阶段 | 内容 | 交付物 | 验收 |
|---|---|---|---|
| **P0 部署与选型验证** | compose 起 RAGFlow + FalkorDB + graphiti-mcp；网关接 OpenAIGenericClient；手动冒烟：上传文档→retrieval；add_memory→search_memory_facts；验证 GLM/网关模型的抽取 JSON 稳定性与中文检索质量、embedding 维度 | deploy/compose 样例 + 验证记录 | 两条链路 curl 全通；抽取结果人工可读 |
| **P1 知识库检索闭环** | `service/knowledge` 客户端与业务层、`tblLlmKnowledgeDataset`、knowledge_search 工具、`<knowledge>` 注入、/react/knowledge/{list,bind,unbind}、指标 | 模型可检索文档回答 | playground 问手册问题，答案含出处；关开关零回归（对齐 memory P1 验收口径） |
| **P2 Graphiti 读闭环** | MCP 动态连接接入（过渡）；`service/graphmemory` REST 客户端；graph_memory_search 工具（服务端强制 group_id）；`<graph_memory>` 注入 | 模型可查图谱事实 | "X 和 Y 什么关系"类问题命中图谱；跨 group 隔离用例通过 |
| **P3 写闭环与管理面** | W1 写工具 + W2 收敛回灌（闸门全配）；本体 YAML；/react/knowledge 文档上传/解析状态/parse-stop；reflection 只读桥接 | 记忆自动沉淀 | 多轮会话后新会话能答出上会话形成的实体关系；episode 成本与延迟有指标观测 |
| **P4 统一检索与运营** | 分流质量评估（必要时联邦检索）；communities/saga 维护任务；memory P4 条件决策 | 运营可观测 | 分流准确率抽检达标 |

每阶段独立开关、默认关闭或灰度，节奏对齐 memory 模块的落地方式。

## 9. 风险与开放问题

| # | 风险/问题 | 对策 |
|---|---|---|
| 1 | RAGFlow 部署重（≥4C8G、多中间件） | P0 先起 slim 配置；确认价值后再投资源；检索 API 收敛在 client 单点，未来可换 LightRAG/自研 |
| 2 | GLM/网关模型做 Graphiti 抽取的 JSON 结构化稳定性不足 | P0 专项验证；不行则 graphiti 侧独立配 OpenAI/Anthropic key（基座零改动） |
| 3 | 中文 BM25/全文检索质量（FalkorDB/Neo4j 分词） | P0 验证；预期靠向量+实体名兜底；必要时换 Neo4j+中文 analyzer |
| 4 | P1 MCP 通道下 group_id 模型可控（越权读写） | P1 仅信任环境/共享图；产品化以 P2 服务端强制注入为界 |
| 5 | episode 写入 LLM 成本（每条 3-4 次调用） | W2 闸门（require_tool_use/冷却/队列上限）+ 指标观测后再放量 |
| 6 | RAGFlow 版本升级 API 漂移 | 只依赖官方 API v1、集中在 client.go；升级锁版本镜像 |
| 7 | 注入块增加 system token 开销 | 双预算上限 + 空不渲染 + 关闭开关零回归；`react_inject_block_chars` 水位指标 |
| 8 | 三层记忆事实冲突 | Layer1 优先原则写进工具文案与注入块头部；reflection W3 桥接对齐 |
