# 本地工作台与服务端基座的执行边界

> 回答一个反复出现的问题：**为什么本地 AI 工作台（Claude Code / ZCode / Cursor 等）能直接执行 hook、检索代码仓库，"实现起来那么简单"；而服务端基座处处是限制（沙箱禁 `open`、hook 只能声明式、检索要走 MCP/worktree）？**
> 本文沉淀这个讨论，作为基座沙箱/插件/hook/检索能力边界的决策依据。
> 关联：[服务端AI工作台改造方案.md](./服务端AI工作台改造方案.md)（P2/P3 能力收窄的出处）、[openhands-sdk学习.md](./openhands-sdk学习.md)（容器化路线的参照）。
> 撰写日期：2026-09-13。

---

## 1. 核心论断

> **本地工作台不是"实现了"这些能力，而是"不需要实现"——隔离由"一台机器一个主人"这个物理事实免费提供。服务端不是做不到，而是必须自己重建这层被多租户打破的边界，全部成本都在"重建"上。**

以 Claude Code 为例：检索代码就是一行 shell（仓库本来就在磁盘上、rg 是现成二进制、进程拥有用户的全部文件权限）；执行脚本/hook 就是 spawn 一个子进程；插件是你自己装的、跑在你机器上，等同于你自己跑脚本。这些"简单"背后有三个**隐含前提**，本地全部白送，服务端全部缺失：

| 隐含前提 | 本地工作台 | 服务端基座 |
|---|---|---|
| **信任边界** | 跑的是用户自己装/写的代码；操作系统用户权限就是边界，"你的机器你做主" | 插件脚本是**第三方代码**；"安装的人、触发执行的人、承担后果的人"三方分离 |
| **影响半径** | 误操作删的是自己的目录；用户在场盯着（交互式） | 一个进程服务 N 用户 N caller；误操作波及生产库/密钥/其他租户；headless 执行时无人在场 |
| **执行环境** | 文件、rg、git、python 全在用户机器上，进程权限 = 用户权限 | 代码仓库在远端 git（先要解决"代码怎么进来"）；执行环境必须显式构造 |

换句话说：**本地工作台把隔离外包给了操作系统和物理边界，它根本没做沙箱。** Claude Code 的 hooks 就是用户机器上 settings.json 里的一条本地命令——它能这么做，是因为单用户信任假设成立。

## 2. 基座的每一处"不能"，都是同一个原因

前几轮讨论的每个限制，拆开都是"必须自建隔离"这一个约束的不同侧面：

| 表面上的限制 | 背后真正的原因 |
|---|---|
| python 沙箱禁 `open`、import 白名单无 os/subprocess/re（见 `sandbox/server.py` 的 `FORBIDDEN_CALLS` / `ALLOWED_IMPORT_ROOTS`） | 多租户下，第三方脚本必须待在"无文件系统、无网络、无子进程"的笼子里——本地这是默认（你的目录随便读），服务端这是必须显式建造的 |
| hook 只做声明式（webhook 回调 + 白名单动作），不执行任意代码 | 本地 hook = 用户自己写的进程；服务端 hook = 任意第三方逻辑获得"改写工具结果/拦截执行"的高权限入口，笼子必须更严 |
| 代码检索走 repo MCP / mirror+worktree，而不是脚本直接扫目录 | 本地"代码就在当前目录"一句话解决了三件事；服务端要分别回答：**代码怎么到服务器**（clone/worktree）、**哪个进程能读**（挂载与路径约束）、**哪个 caller 能看哪个仓库**（权限模型） |
| Bundle 的 scripts/ 限定 python 沙箱（stdin 进、stdout 出） | 脚本是计算插件（分析已取到的数据/代码），不是执行环境；"检索+分析"的正确组合是：repo MCP 取代码 → python_exec 做 AST/统计/校验分析 |

## 3. OpenHands 的标准答案：花钱买回本地边界

服务端要获得"本地工作台级别的自由度"，业界已验证的路径是 **把"本地机器"搬进容器**：

```text
OpenHands：每会话一个 Docker 容器，agent-server 跑在容器里
  → 容器内重新获得"一台机器一个主人"的全部自由：
    terminal、任意 shell、hook、rg 随便跑、文件随便写
  → 代价：容器编排、workspace 生命周期管理、镜像分发、暖池（见 openhands-sdk学习.md §4）
```

它不是更聪明，是用一整套基础设施成本换回了本地免费的边界。这印证了基座方案里"不引入每会话一容器模型"的取舍：对**多租户中心化服务**，这个成本只有在特定场景（深度代码改造、任意 shell 需求）才值得付。

## 4. 基座的等价物映射（收窄是正确解，不是妥协）

```text
本地工作台能力        →  服务端基座等价物（现有方案）
─────────────────────────────────────────────────────
rg / 读文件          →  repo MCP + git mirror/worktree（服务端自己的受控代码在读，权限在基座手里）
本地任意脚本          →  python_exec 沙箱（stdin 进 stdout 出的最小笼子）
本地 hook            →  声明式 hook（webhook 回调 + 白名单动作，不执行第三方逻辑）
terminal 自由执行    →  不做（= 拒绝把每会话一容器的成本引进基座）
```

## 5. 未来逃生通道（何时升级边界）

如果将来出现真实需求要求"本地级自由度"（例如：让 agent 直接改代码并跑测试，而不只是排障检索），路径是明确的：

1. **独立部署形态**：为该类 run 分配容器化 workspace（OpenHands 模式），作为**独立部署单元**接入基座（基座经 RemoteWorkspace 式 API 驱动），而不是把容器编排内置进基座；
2. 届时再评估：容器池、镜像管理、会话-容器生命周期、成本核算；
3. 判断标准：**只读检索类需求永远不需要它**（repo MCP 足够）；只有"必须执行任意构建/测试/shell"的场景才值得付这个成本。

## 6. 一句话结论

> 本地工作台的"简单"是单用户信任模型 + 操作系统边界 + 用户在场监督的免费赠品；服务端基座的每个"限制"都是在多租户环境下重建等价安全边界的必要成本。基座方案对沙箱/hook/检索的收窄，是在信任模型正确的前提下做的正确解。
