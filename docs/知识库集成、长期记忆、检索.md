### 1. Mem0：最值得先看“长期记忆怎么做”

这是我最推荐你先读的项目之一，目前 GitHub 大约 **65k stars**，定位非常明确：

> 给 Agent 提供独立的 Memory Layer。

它不是简单把历史聊天全部 embedding，而是从交互里抽取真正值得记住的信息，例如：

```text
原始对话
↓
Memory Extractor
↓
事实 / 偏好 / 决策 / 事件
↓
Memory Store
↓
Hybrid Retrieval
↓
Relevant Memories
```

例如：

```text
用户：
我们线上 Hive SQL 查询慢的问题最后发现是上游表没有加速。

↓ Memory

{
  type: "incident_resolution",
  system: "Hive",
  problem: "SQL查询慢",
  rootCause: "上游表未加速"
}
```

等以后 Agent 再遇到类似问题，就可以主动召回。

Mem0 在 2026 年还更新了新的 memory algorithm，强调 **ADD-only extraction、semantic + BM25 + entity matching、多信号检索以及时间相关召回**。它也支持自托管 Server 和 REST API，所以即便你的业务端是 Go，也没必要把 Memory Engine 重写成 Go。([GitHub][1])

[Mem0 GitHub](https://github.com/mem0ai/mem0?utm_source=chatgpt.com)

### 2. Graphiti：如果你的记忆会不断“变化”，这个非常值得研究

Graphiti 是 Zep 背后的开源 temporal knowledge graph 框架。

它和 Mem0 最大的区别是：

**Graphiti 把 Memory 看成随时间变化的“事实图谱”。**

比如：

```text
2026-08
service-A → deployed_on → cluster-01

2026-09
service-A → deployed_on → cluster-02
```

普通 RAG 很可能搜索出来两个冲突答案。

Graphiti 会记录事实的有效时间，因此可以区分：

```text
现在 service-A 在哪里？
→ cluster-02

8 月的时候在哪里？
→ cluster-01
```

它维护：

```text
Episode
  ↓
Entity
  ↓
Relationship
  ↓
Valid From / Valid To
```

同时支持：

```text
Semantic Search
+
BM25
+
Graph Traversal
+
Temporal Filtering
```

而且每个事实还能追溯到原始 Episode，即 provenance。

对于**运维 Agent、事故分析、系统拓扑、配置变化、部署历史、问题解决经验**，这种模型其实比单纯 Vector DB 更自然。([GitHub][2])

[Graphiti GitHub](https://github.com/getzep/graphiti?utm_source=chatgpt.com)

### 3. Cognee：我觉得是目前“知识库 + Memory”结合得最值得看的一个

如果你的问题恰好是：

> 有没有一个项目，既能做企业知识库，又能做 Agent 长期记忆？

我会重点看 **Cognee**。

目前大约 **30k stars**。它自己的定位就是：

> Open-source AI memory platform / knowledge engine.

它不是只做：

```text
Document
→ Chunk
→ Embedding
→ Vector DB
```

而是：

```text
Documents
Conversations
Events
Structured Data
        │
        ▼
     Cognee

 ▼             ▼
Vector        Graph
Store         Store
```

Cognee 的 `recall` 会自动选择适合的 retrieval strategy，同时它也允许显式执行 graph-aware retrieval。

官方明确强调：

这就使它特别适合：

```text
企业文档

用户记忆
```

放进统一 Context Engine。([GitHub][3])

[Cognee GitHub](https://github.com/topoteretes/cognee?utm_source=chatgpt.com)

### 5. Letta：重点不是“检索”，而是“Agent 怎么管理自己的记忆”

Letta，也就是以前的 **MemGPT**。

它非常值得研究架构思想。

它会把 Agent Memory 分成类似：

```text
Context Window

┌─────────────────────────┐
│ System                  │
├─────────────────────────┤
│ Persona Memory          │
├─────────────────────────┤
│ Human/User Memory       │
├─────────────────────────┤
│ Working Memory          │
├─────────────────────────┤
│ Conversation            │
└─────────────────────────┘
```

其中 Memory Block 是持久化的，并且可以：

```text
attach
detach
update
share between agents
```

官方明确把 Block 定义成 Agent context window 中的持久区域，而且同一 Block 可以共享给多个 Agent。([Letta Docs][6])

所以 Letta 最值得学习的是：

**Memory 如何进入 Agent Runtime。**

而 Mem0 / Graphiti 更偏：

**Memory 如何存储和检索。**

这两个方向是不一样的。

[Letta GitHub](https://github.com/letta-ai/letta?utm_source=chatgpt.com)

## 1. 先建立 Graphiti 的正确心智模型

传统 RAG 通常是：

```text
文档
  ↓
Chunk
  ↓
Embedding
  ↓
Vector DB
  ↓
Similarity Search
  ↓
Context
```

Graphiti 则更像：

```text
                     Episode
                  原始事件 / 对话
                        │
                        │ LLM抽取
                        ▼
              ┌─────────────────┐
              │     Entity      │
              │  实体识别/去重   │
              └────────┬────────┘
                       │
                 Relationship
                       │
                       ▼
              ┌─────────────────┐
              │      Fact       │
              │   事实 + 时间    │
              └─────────────────┘
                       │
                       ▼
               Temporal Graph
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       Vector         BM25       Graph BFS
          │            │            │
          └────────────┼────────────┘
                       ▼
                  Hybrid Search
```

Graphiti 官方把自己定义为构建 **Temporal Knowledge Graph / Context Graph** 的框架，它支持增量更新，不需要每次重新构建整个知识库。 ([Zep][1])

# 2. Graphiti 最重要的三个对象

先只记住三个。

### EpisodicNode

它表示：

> “发生过的一次事情”。

例如你的运维 Agent：

```text
2026-09-10 10:32

用户：
为什么 hive_job_123 执行很慢？

Agent：
排查发现上游表 ods_order 没有完成加速。
```

整个事件就可以作为一个 Episode。

Graphiti 支持三种主要 Episode：

```text
text
message
json
```

并且 Episode 自己也是图中的节点；从 Episode 抽取出来的实体，会通过 `MENTIONS` 边与 Episode 建立联系，因此最终事实可以追溯到原始来源。 ([Zep][2])

可以理解成：

```text
Episode
   │
   ├──MENTIONS──> hive_job_123
   │
   ├──MENTIONS──> ods_order
   │
   └──MENTIONS──> 加速任务
```

---

### EntityNode

Entity 就是长期稳定存在的“东西”。

源码里的 `EntityNode` 主要包含：

```text
name
name_embedding
summary
attributes
labels
group_id
...
```

当前源码中 `EntityNode` 本身就保存 `name_embedding`、summary 和 attributes。 ([GitHub][3])

例如运维场景可以有：

```text
Service
Table
Job
Cluster
Dataset
User
Incident
Error
```

于是：

```text
ods_order
```

可能是：

```text
EntityNode

name = ods_order
type = Table

attributes = {
    database: "ods",
    owner: "xxx"
}
```

---

### EntityEdge

这是 Graphiti 真正特别重要的部分。

Graphiti 把大量“知识”存在 **边上，而不是节点上**。

例如：

```text
ods_order
    │
    │ NOT_ACCELERATED
    ▼
hive_job_123
```

真正保存的是：

```text
fact:
"hive_job_123 查询缓慢是因为 ods_order 没有加速"
```

当前 `EntityEdge` 包含：

```text
name
fact
fact_embedding

source_node_uuid
target_node_uuid

episodes

created_at
valid_at
invalid_at
expired_at
reference_time
```

所以 Graphiti 的 Edge 不只是：

```text
A -> B
```

而是：

```text
A
 ──────────────→ B

关系：
DEPENDS_ON

事实：
job_123 depends on ods_order

有效时间：
valid_at = ...

失效时间：
invalid_at = ...

来源：
episode_123
```

这就是 Graphiti 和普通 Knowledge Graph 很大的区别。 ([GitHub][4])

# 3. 为什么叫 Temporal Knowledge Graph

这是 Graphiti 最值得研究的地方。

假设 8 月：

```text
service-A
DEPLOYED_ON
cluster-01
```

到了 9 月：

```text
service-A
DEPLOYED_ON
cluster-02
```

传统 RAG 很可能最终存在：

```text
service-A -> cluster-01

service-A -> cluster-02
```

然后你问：

```text
service-A 现在在哪？
```

两条都可能搜出来。

Graphiti 会给 Fact 加时间信息：

```text
Fact A

service-A -> cluster-01

valid_at   = 2026-08-01
invalid_at = 2026-09-01
```

新的：

```text
Fact B

service-A -> cluster-02

valid_at   = 2026-09-01
invalid_at = null
```

Graphiti 当前源码确实会在发现新事实与旧事实冲突，并且新事实生效时间更晚时：

```text
old_edge.invalid_at = new_edge.valid_at
old_edge.expired_at = now
```

也就是说旧事实没有被简单删除，而是保留成历史。 ([GitHub][5])

这就是为什么它特别适合：

```text
配置变化
部署历史
系统拓扑变化
用户偏好变化
负责人变化
事故状态变化
数据依赖变化
```

# 4. Graphiti 实际上有“两套时间”

理解这一点非常重要。

可以简单理解：

```text
                  时间
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
    Event Time          System Time
    业务世界时间          Graphiti处理时间
```

比如：

```text
事件真实发生：
8 月 10 日 service-A 迁移到了 cluster-B

Graphiti 得知这件事：
9 月 13 日
```

那么：

```text
valid_at
≈ 8 月 10 日

created_at / expired_at
≈ Graphiti 什么时候写入/处理
```

Graphiti 甚至在新的 Saga 实现里明确区分了：

```text
created_at
= ingestion / wall-clock time

valid_at
= episode reference/event time
```

源码注释明确说明，即使今天才补录一条很久以前发生的 Episode，它的 `created_at` 仍然是今天，而 `valid_at` 可以是历史时间。 ([GitHub][6])

这就是 **bi-temporal** 思想的重要来源。

# 5. `add_episode()` 是你学习源码的第一核心入口

以后我们深入源码，第一条主线就追：

```text
Graphiti.add_episode()
```

不要一开始乱看整个仓库。

它的大致执行链路可以抽象成：

```text
add_episode()

      │
      ▼

创建 EpisodicNode
      │
      ▼

读取 previous episodes
      │
      ▼

extract_nodes()
      │
      │ LLM
      ▼

候选 Entity
      │
      ▼

resolve_extracted_nodes()
      │
      ├─ Entity 去重
      ├─ Entity 对齐
      └─ 合并已有 Entity
      │
      ▼

extract_edges()
      │
      │ LLM
      ▼

候选 Fact / Relationship
      │
      ▼

resolve_extracted_edges()
      │
      ├─ Edge 去重
      ├─ Fact 去重
      ├─ 冲突检测
      └─ 时间失效处理
      │
      ▼

Embedding
      │
      ▼

写入 Graph DB
```

现在源码里可以直接看到：

```text
_extract_and_resolve_nodes()

extract_nodes()
      ↓
resolve_extracted_nodes()
```

以及：

```text
_extract_and_resolve_edges()

extract_edges()
      ↓
resolve_edge_pointers()
      ↓
resolve_extracted_edges()
```

([GitHub][6])

这两条链路基本就是 **Graphiti Memory Write Pipeline 的核心**。

# 6. 为什么一定要 Entity Resolution

假设 Agent 连续收到：

```text
Episode 1:
MySQL 服务出现异常

Episode 2:
mysql-service 出现连接超时

Episode 3:
MySQL 集群恢复
```

LLM 可能抽出来：

```text
MySQL
mysql-service
MySQL集群
```

如果全部直接入图：

```text
MySQL

mysql-service

MySQL集群
```

那长期记忆很快就乱了。

Graphiti 因此有：

```text
extract_nodes
       ↓
resolve_extracted_nodes
       ↓
Canonical Entity
```

最终尽量归一成：

```text
Entity:
mysql-service
```

这也是长期记忆系统比简单：

```text
conversation -> embedding
```

复杂得多的原因。

# 7. Graphiti 的读取链路也非常值得学

Graphiti 默认不是纯 Vector Search。

现在核心检索能力包括：

```text
Semantic Search
+
BM25
+
Graph Search / BFS
+
Reranking
```

默认 `search()` 的 Hybrid Search 会结合 semantic similarity 和 BM25，然后使用 RRF 融合；如果提供 focal node，还可以根据图距离重新排序。 ([Zep][7])

源码可以看到：

```text
edge_search()

 ├─ edge_fulltext_search()
 │       BM25
 │
 ├─ edge_similarity_search()
 │       Vector
 │
 └─ edge_bfs_search()
         Graph
```

Node 也基本一样：

```text
node_search()

 ├─ node_fulltext_search()
 ├─ node_similarity_search()
 └─ node_bfs_search()
```

然后：

```text
              BM25
                │
Vector ─────────┼──────── Graph
                │
                ▼
              RRF
                │
                ▼
           Search Result
```

当前源码的确是根据 `SearchConfig` 并发执行 BM25、cosine similarity 和 BFS，再统一 rerank。 ([GitHub][8])

这比：

```text
cosine(query_embedding, chunk_embedding)
```

强很多。

([GitHub][3])

# 9. Graphiti 允许自己定义 Ontology

这个对你的场景特别重要。

Graphiti 不要求你永远只有：

```text
Entity
RELATES_TO
Entity
```

可以通过 Pydantic 自己定义：

```python
class Service(BaseModel):
    owner: str | None = None
    language: str | None = None


class Table(BaseModel):
    database: str | None = None
    table_type: str | None = None
```

以及：

```text
Service -> DEPENDS_ON -> Service

Job -> READS_FROM -> Table

Incident -> AFFECTS -> Service
```

Graphiti 会在 Episode ingestion 时尝试完成：

```text
实体抽取
↓
实体类型分类
↓
属性抽取
↓
关系类型分类
↓
关系属性抽取
```

官方还支持通过 `edge_type_map` 限制某类节点之间允许出现哪些关系。 ([Zep][9])

## 我建议我们下一步重点拆 `add_episode()`

如果按照你之前学习 Letta 源码的方式，我认为接下来最有价值的是直接沿：

```text
add_episode
   ↓
extract_nodes
   ↓
resolve_extracted_nodes
   ↓
extract_edges
   ↓
resolve_extracted_edges
   ↓
resolve_edge_contradictions
   ↓
save
```

把这一整条**记忆写入链路逐函数拆开**。

尤其值得弄清楚三个问题：

1. **LLM 到底调用了几次，每一次负责什么；**
2. **Graphiti 怎么判断两个 Entity/Fact 是重复还是冲突；**
3. **新 Episode 到来以后，旧记忆究竟如何更新而不是覆盖。**

这三部分搞懂之后，Graphiti 大约 **70% 的核心设计思想**就已经掌握了。下一步最适合直接从 `Graphiti.add_episode()` 源码开始逐段分析。

[9]: https://help.getzep.com/graphiti/core-concepts/custom-entity-and-edge-types?utm_source=chatgpt.com "Custom Entity and Edge Types | Zep Documentation"
[10]: https://github.com/getzep/graphiti?_bhlid=183f85afce84b040bb160893f79048139badd71b&utm_source=chatgpt.com "GitHub - getzep/graphiti: Build Real-Time Knowledge Graphs for AI Agents · GitHub"

Graphiti和Letta有什么区别
差别其实很大。最核心的一句话是：

> **Graphiti 是“长期记忆/知识检索引擎”，Letta 是“带长期记忆能力的完整 Agent Runtime”。**

所以它们并不是严格意义上的同类产品。

### 核心区别

| 维度                 | Graphiti                               | Letta                                             |
| ------------------ | -------------------------------------- | ------------------------------------------------- |
| 产品定位               | Temporal Context Graph / Memory Engine | Stateful Agent Runtime / Harness                  |
| 是否包含 Agent Runtime | ❌                                      | ✅                                                 |
| 是否负责 LLM 调用循环      | 基本不负责                                  | ✅                                                 |
| 是否负责工具调用           | ❌，主要提供记忆能力                             | ✅                                                 |
| 是否管理 Agent 上下文窗口   | ❌                                      | ✅，这是核心能力之一                                        |
| 记忆结构               | Episode → Entity → Fact/Edge           | Message History + Memory Blocks + External Memory |
| 图结构                | ✅ 核心设计                                 | 不是核心                                              |
| 时间关系               | ✅ 非常强，Fact 有有效期                        | 有历史和持续状态，但不是 temporal KG 模型                       |
| 事实冲突               | 新事实可使旧事实失效，保留历史                        | Agent/Memory 机制负责更新长期上下文                          |
| 检索                 | Vector + BM25 + Graph Traversal        | Recall / Memory / Files 等                         |
| Agent 能否主动修改自己的记忆  | 不是核心模式                                 | ✅ 非常核心                                            |
| 适合                 | 给已有 Agent 增加长期知识/记忆服务                  | 直接搭建一个持久化 Agent                                   |

Graphiti 官方现在把自己定义为构建 **Temporal Context Graph** 的框架：不断把用户交互、结构化数据、非结构化数据增量转换成实体和事实，并支持 semantic、keyword 和 graph traversal 混合查询。([GitHub][1])

而 Letta 当前直接把自己定位为：

> platform for building stateful agents

完整包含 Agent Harness、App Server、Channels、Agent SDK、记忆和运行时。([Letta Docs][2])

## 1. 两者对“Memory”的理解完全不同

这是最值得理解的地方。

### Graphiti：Memory = 世界中发生过的事实

Graphiti 更关注：

```text
发生了什么？
谁和谁有什么关系？
这个关系什么时候成立？
什么时候不再成立？
这个事实来自哪里？
```

例如：

```text
Episode 1：

2026-08-01
service-A 部署在 cluster-01
```

形成：

```text
service-A
    │
    │ DEPLOYED_ON
    ▼
cluster-01

valid_at = 2026-08-01
```

后来：

```text
Episode 2：

2026-09-01
service-A 已迁移到 cluster-02
```

Graphiti 可以形成：

```text
旧 Fact：

service-A → cluster-01

valid_at   = 2026-08-01
invalid_at = 2026-09-01


新 Fact：

service-A → cluster-02

valid_at   = 2026-09-01
invalid_at = null
```

所以 Graphiti 的长期记忆实际上接近：

```text
Agent 对世界的长期事实模型
```

而且所有事实可以追溯回原始 Episode。Graphiti 官方现在明确强调 **fact validity window、provenance 和 bi-temporal tracking**。([GitHub][1])

---

# 2. Letta：Memory = Agent 自己的持续状态

Letta 思考的不是：

> 世界里有哪些 Entity？

而是：

> **这个 Agent 下一次醒来时，需要知道什么？**

比如一个开发 Agent：

```text
Agent ID: agent_123

Memory:

[self]
我是项目的后端开发助手。

[user]
用户主要使用 Go。
代码示例习惯使用格式化占位符。

[project]
项目使用：
Gin
GORM
MySQL
Redis
Kafka

[workflow]
提交代码前先运行 go test ./...
```

这些东西不是知识图谱。

而是直接影响：

```text
System Prompt
+
Current Context
+
Agent Behavior
```

Letta 当前把 Memory Block 视为**持久化、可编辑的 context segment**；Agent 本身可以通过 memory 工具修改这些 Block。([Letta][3])

当前 Letta Code 的设计更进一步，把记忆划分成：

```text
Agent
 │
 ├── Message History
 │     │
 │     └── 过去经历
 │
 ├── Memory Blocks
 │     │
 │     └── 当前最重要、直接进入上下文的知识
 │
 └── External Memory
       │
       ├── Skills
       ├── Markdown
       └── Files
```

它明确强调 Memory Block 是有限的“context real estate”，详细信息应该进入 external memory，需要的时候再找回来。([GitHub][4])

所以 Letta 更像：

```text
Agent自己的大脑
```

Graphiti 更像：

```text
Agent可以查询的长期世界模型
```

# 3. 一个例子就能看出差别

假设做一个**智能运维 Agent**。

出现一次事故：

```text
2026-09-10

job_123 SQL 执行耗时从 2min 上升到 30min。

Agent 排查：

job_123
   ↓ depends_on
ods_order

ods_order 的加速任务失败。

重新执行加速任务以后恢复。
```

### Graphiti 会更倾向记成

```text
                 READS_FROM
job_123 ─────────────────────→ ods_order
                                 │
                                 │ HAD_FAILURE
                                 ▼
                         acceleration_task
                                 │
                                 │ CAUSED
                                 ▼
                            incident_001
                                 │
                                 │ RESOLVED_BY
                                 ▼
                       rerun_acceleration
```

以及：

```text
什么时候发生
什么时候恢复
事实来源 Episode
实体关系
历史版本
```

以后问：

```text
ods_order 最近发生过哪些事故？

job_123 为什么以前变慢过？

哪些 Job 曾因为加速失败出现问题？
```

Graphiti 特别擅长。

---

### Letta 更倾向记成

Agent 根据这次经验更新：

```text
[operations_knowledge]

排查 SQL 性能问题时：
1. 检查上游数据依赖
2. 检查上游表加速状态
3. 检查最近加速任务失败情况
```

下一次出现：

```text
SQL 又慢了
```

Agent 的行为直接变成：

```text
先执行：

check_dependency()
check_acceleration_status()
```

这其实是：

> **经验 → 行为改变**

而不仅仅：

> **经验 → 可搜索的数据**

这正是 Letta 的核心思想之一——Agent 可以通过持续修改自身 context / memory 来学习。当前 Letta Code 甚至把这种机制描述为持续的 experiential / persistent agent。([GitHub][4])

# 4. 两者最大的架构差异

可以这样理解。

### Graphiti

```text
                      Your Agent
                          │
            ┌─────────────┼─────────────┐
            │             │             │
           LLM           Tools        Graphiti
                                        │
                                   Memory API
                                        │
                         ┌──────────────┼──────────────┐
                         │              │              │
                      Episode        Entity          Fact
                         │              │              │
                         └──────────────┼──────────────┘
                                        │
                                    Graph DB
```

Graphiti基本处于：

```text
Agent 外部
```

它是基础设施。

官方开源版本目前需要自己提供 Neo4j、FalkorDB、Amazon Neptune 等图存储，而且 Graphiti 自己并不提供用户、Conversation 管理和完整 Agent Runtime。([GitHub][1])

---

### Letta

则是：

```text
                         Letta Agent
                             │
                  ┌──────────┼──────────┐
                  │          │          │
                 LLM       Memory      Tools
                  │          │          │
                  │     ┌────┴────┐     │
                  │     │         │     │
                  │   Blocks    Recall  │
                  │     │         │     │
                  └─────┼─────────┼─────┘
                        │
                 Context Manager
                        │
                   Agent Runtime
                        │
              Persistence / Server
```

也就是说：

> **Memory 是 Runtime 的一部分。**

这也是为什么 Letta 能直接做：

```text
Agent
Conversation
Memory
Tool
Channel
Schedule
Runtime
Server
```

而 Graphiti 没打算替你解决这些问题。([Letta Docs][2])

# 5. 谁负责“决定记什么”也不同

这个差异非常重要。

## Graphiti

你通常：

```text
Conversation/Event
        ↓
add_episode()
        ↓
Graphiti
        ↓
LLM extraction
        ↓
Entity
        ↓
Fact
        ↓
Resolve / Dedup
        ↓
Temporal Graph
```

Graphiti 更像：

> **系统自动整理记忆。**

Agent 不需要自己写：

```text
我应该把 ods_order 保存到哪一个 memory block？
```

Graphiti负责结构化。

---

## Letta

则强调：

```text
Agent
 ↓
发现重要信息
 ↓
调用 memory 工具
 ↓
修改自己的 Memory
```

例如 Agent 自己判断：

```text
这件事情以后很重要
```

然后：

```text
memory_replace(...)
```

改变自己的长期 context。

所以这是：

> **Agent 自主管理记忆。**

这也是 MemGPT / Letta 非常有特色的地方。

# 6. 检索理念也不同

Graphiti天然是一个**Retrieval System**。

查询：

```text
为什么 job_123 曾经执行很慢？
```

可以综合：

```text
Semantic Search
        +
BM25
        +
Graph Traversal
        +
Temporal Constraint
```

Graphiti 官方明确把 Hybrid Retrieval 作为核心能力。([GitHub][1])

Letta则首先考虑：

```text
什么 Context 应该进入 Agent 当前这一轮思考？
```

它有：

```text
Memory Blocks      ← 永远/经常在context
Message History    ← Agent过去经历
External Memory    ← 需要时检索
```

所以：

```text
Graphiti：

Query
 ↓
Find Knowledge


Letta：

Agent
 ↓
Manage Context
 ↓
Reason
 ↓
Need more information?
 ↓
Retrieve Memory
```

这是两个不同抽象层。

如果**已经有自己的 Agent Runtime**，只是想增加长期记忆：

我不会建议为了 Memory 把整个 Runtime 换成 Letta。

更自然的是：

```text
你自己的 Agent 基座
        │
        ├── LLM
        ├── MCP Client
        ├── Tool Calling
        ├── HITL
        ├── Context Manager
        │
        └── Memory Service
                  │
                  ▼
               Graphiti
```

而且 Graphiti 本身已经提供实验性的 MCP Server，可以直接暴露 Episode、Entity、Relationship、Search、Group 等能力。([GitHub][1])

这样 Go 基座不需要理解 Neo4j 的全部细节，只需要：

```text
Go Agent
   │
   │ MCP / HTTP
   ▼
Memory Service
   │
   ▼
Graphiti
   │
   ▼
Neo4j / FalkorDB
```

相反，如果你的目标变成：

> “我不想自己实现 Agent Runtime、上下文压缩、长期记忆、工具、Schedule、Channel，我需要一个完整的服务端 Agent 平台。”

那 Letta 的抽象层级更合适。

## 最后可以把二者记成一句非常简单的话

```text
Letta
=
如何让「一个 Agent」活得越来越久，
并且不断改变自己的 Context / 行为。


Graphiti
=
如何让「一个 Agent」对世界的认识越来越丰富，
并且知道事实之间的关系以及它们什么时候成立。
```

所以对于**运维 Agent**，我其实很看好：

```text
Agent Runtime
        +
Letta式 Core Memory 思想
        +
Graphiti Temporal Knowledge Memory
```

而不是二选一。尤其像**系统拓扑、任务依赖、故障历史、根因、修复方案、配置变化**这种信息，Graphiti 的 Entity + Fact + Episode + Temporal 模型比单纯的 Letta Memory Block 更匹配。

是，我也更倾向 **RAGFlow Admin**。因为你关注的是“怎么把 RAGFlow 真正接进自己的系统”，而不是再找一个完整知识库成品。

它的架构和你的场景很贴：

```text
你的业务系统 / Agent 平台
        │
        │ HTTP / SDK
        ▼
  自己的知识库服务层
        │
        ▼
     RAGFlow
        │
        ├── Dataset
        ├── Document
        ├── Parsing
        ├── Retrieval
        └── Chat / Agent
```

RAGFlow Admin 本身就是独立部署的管理系统，并没有把 RAGFlow 源码直接揉进来，而是通过 `ragflow-sdk` 调 RAGFlow；它的后端是 Quart，前端是 React + UmiJS + TypeScript + Ant Design，目录也很清晰：`api/apps` 做路由，`api/services` 做业务逻辑，`web/src/services` 负责前端 API 调用。([GitHub][1])

### 对你最值得参考的是这 4 块

第一块是 **RAGFlow Adapter 层**。你真正该学的不是它的页面，而是：

```text
业务 API
   ↓
Service
   ↓
ragflow-sdk
   ↓
RAGFlow
```

以后你完全可以换成 Go：

```text
Gin API
   ↓
Knowledge Service
   ↓
RAGFlow Client
   ↓
RAGFlow HTTP API
```

这样你的 Agent 基座永远不知道底层是不是 RAGFlow。

第二块是 **知识库管理闭环**。RAGFlow Admin 已经把实际产品需要的管理面补出来了，包括跨知识库管理、文档上传/解析/停止/删除、全局解析任务队列、Chat、Agent、用户和系统健康检查。([GitHub][1])

所以你可以直接参考它，把自己的知识库能力定义成：

```text
Knowledge Base
 ├── 创建知识库
 ├── 修改知识库
 ├── 删除知识库
 ├── 文档上传
 ├── 文档解析
 ├── 解析状态
 ├── Chunk查看
 ├── Retrieval Test
 └── 权限管理
```

第三块是 **任务状态管理**。这个其实很重要。

文档进入 RAG 系统不是同步链路：

```text
Upload
  ↓
Parsing
  ↓
Chunking
  ↓
Embedding
  ↓
Indexing
  ↓
Ready
```

所以管理端一定要知道：

```text
pending
running
success
failed
```

RAGFlow Admin 已经专门做了全局 Task Queue、解析进度、队列位置、批量控制。([GitHub][1])

这个设计对你以后做企业知识库很有参考价值。

第四块是 **不要让业务直接调用 RAGFlow**。

我建议你最终不要这样：

```text
Agent
   ↓
RAGFlow API
```

而是：

```text
                        Agent
                          │
                          ▼
                  Knowledge Service
                    你自己实现
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
       Search           Document       Dataset
          │               │               │
          └───────────────┼───────────────┘
                          ▼
                   RAGFlow Adapter
                          │
                          ▼
                       RAGFlow
```

这样以后：

```text
RAGFlow
   ↓
LightRAG
   ↓
自研 Retriever
```

都可以替换，Agent 层完全不用改。
